# Stage 3: DT Check (Логический аудит ДТ)
Используется совместно с `alta\prompt\{primary_tools.md, dt_rules.md}`.

## 1. Назначение
Этап 3 — финальный семантический контроль декларации.
Вход: целевой XML (`dt.xml` перед импортом ИЛИ выгрузка из Альты после правок менеджера).
Цель: сверка полей XML с первичными документами и `master_data`, выявление логических ошибок, опечаток, несоответствий и 
некорректных ручных правок.

## 2. Входные данные и Режимы
При старте AI запрашивает у оператора:
1. **Режим проверки**:
  - `pre_import`: Проверка нашего `dt.xml` перед загрузкой в Альту. Пропускается проверка таможенной стоимости 
     (ДТС, гр. 45, 47).
  - `post_export`: Проверка выгрузки из Альты.
   
2. **Путь к проверяемому XML:**
  - `alta\result\<Кейс>\alta_import\dt.xml` - режим `pre_import`,
  - `alta\result\<Кейс>\alta_export\GDT*.xml` - `post_export`,

3. **Источник первички**: На что опираться?
   - `*.md` (текстовые версии из `alta\source\...\md\`).
   - Оригиналы (pdf/docx, если AI может их читать).
   - `master_data` и `operator_provided_data.md` используются всегда.

## 3. Формат вывода (Отчет)
По результатам проверки AI формирует отчет `alta\result\<Кейс>\review\{ dt_check_review.md | GDT_check_review.md}`.
Формат отчета:
```markdown
# Отчет по этапу 3 (Логический аудит ДТ)

## 1. Мета
- Кейс: <Кейс>
- Режим: <pre_import / post_export>
- Проверяемый файл: <путь к XML>
- Источник первички: <*.md / оригиналы>

## 2. Сводка
- Всего проверено полей: <N>
- Ошибок (Error): <N>
- Предупреждений (Warning): <N>

## 3. Детализация ошибок и предупреждений
| Поле ДТ | Значение в ДТ | Значение в первичке | Статус | Комментарий |
|---------|---------------|---------------------|--------|-------------|
| G_8_NAM | ООО РОМАШКА  | ООО "РОМАШКА"       | Error  | Не совпадает |

## 4. Блокеры
- <критическая ошибка, препятствующая подаче>
```

## 4. Правила парсинга XML
- Выгрузка из Альты содержит служебные теги (`___NUM`, `PARENT_ID`, `D_*`, `FACE`, `ED_ID`, `DOCTEXT`, расчеты `G_45`, 
  `G_47`, `G_12`). **ИХ НУЖНО ИГНОРИРОВАТЬ**.
- Извлекать и анализировать только meaningful-теги (начинаются с `G_`).
- В режиме `post_export` учитывать, что менеджер мог округлить значения (веса) или изменить текст. Если изменение логично 
  (округление) — Warning, если ломает логику (нетто > брутто) — Error.

## 5. Правила логического аудита (по разделам ДТ)

### 5.1 Идентификация и Стороны (Графы 1, 2, 8, 9, 14)
- **Графа 2 (Отправитель)**: Наименование, адрес, страна (код и название) должны совпадать с инвойсом/контрактом.
- **Графы 8, 9, 14 (Получатель, Финансы, Декларант)**: Если `G_8_SM14` или `G_9_SM14` = `true`, данные должны дублировать 
  Графу 14. Декларант сверяется с `master_data` (ИНН/КПП, ОГРН, адрес, паспортные данные доверенного лица).

### 5.2 Транспорт и Условия поставки (Графы 15-21)
- **Графы 15, 16, 17**: Коды и названия стран. Страна отправления и назначения должны логически соответствовать маршруту.
- **Графа 18, 21**: При авиаперевозке (наличие AWB) графы 18 должны быть пустыми, 21 — номер рейса и страна `00`. 
  При авто — номер ТС и страны регистрации.
- **Графа 20**: Условия поставки (Incoterms) и место должны совпадать с инвойсом/контрактом.

### 5.3 Финансы и Сделка (Графы 22, 24)
- **Графа 22**: Код валюты (числовой и буквенный) и общая сумма по инвойсу. Проверить, что сумма всех `<G_42_1>` по 
  товарам равна `<G_22_2>`.
- **Графа 24**: Характер сделки. Обычно 010 (возмездная). Проверить на типичные опечатки.

### 5.4 Товары (Массив BLOCK, Графы 31-47)
Для каждого `<BLOCK>` проверяем:
- **Графа 31**: Описание (`<NAME>`), производитель, ТМ. В режиме `post_export` обращать внимание на изменения текста 
  менеджером.
- **Графа 33**: Код ТН ВЭД. Проверить, что он соответствует описанию товара.
- **Графа 34**: Код страны происхождения. Должен совпадать со страной отправителя/производителя.
- **Графы 35, 38 (Веса)**: 
  - Нетто (`G_38_1`) <= Брутто (`G_35_1`).
  - В режиме `post_export`: веса могут быть округлены до 3 знаков (или целых). Если менеджер изменил вес, проверить, 
    не сломалась ли пропорция (нетто не может стать больше брутто).
  - Сумма весов нетто всех товаров должна быть = Общему весу нетто по СМР/AWB. То же для брутто.
- **Графа 41, 31.8**: Количество и доп. единица измерения. Сверить с упаковочным листом и инвойсом. Код ЕИ должен 
  соответствовать ТН ВЭД.
- **Графа 42**: Стоимость товара. Сумма всех `G_42_1` должна совпадать с инвойсом.
- **Графа 44 (Документы)**:
  - Сверить наличие обязательных документов: Контракт, Инвойс, Упаковочный лист, Транспортная накладная, Платежка, 
    Доверенность, Паспорт.
  - Проверить номера и даты. В `post_export` менеджер мог добавить `G442R` (номер ДТ, где применялся документ) — это норма.
  - В `pre_import` тег `G442R` должен отсутствовать.

### 5.5 Таможенная стоимость (Графы 45, 47) — только для `post_export`
- Проверить наличие тегов `G_45_0`, `G_45_1`, `G_47_1_1` и др.
- Сумма таможенных платежей не должна быть отрицательной.
- Проверить логику: ставка пошлины/НДС умноженная на базу должна приблизительно сходиться с начисленными платежами.

### 5.6 Прочие графы (29, 30, 54)
- **Графа 29**: Код и наименование таможни. Должны совпадать с `master_data`.
- **Графа 30**: Номер СВХ. Сверить с `non_formalized.svh` или транспортным документом.
- **Графа 54**: Данные доверенного лица (ФИО, паспорт, доверенность). Строгое совпадение с `master_data`. В `post_export` 
  дата подачи (`G_54_20`) должна быть актуальной.

## 6. Алгоритм: ДЕТЕРМИНИРОВАНО (СТРОГО ПО ПУНКТАМ)

### 6.1 Разведка и Подготовка
1. Вспомни ограничения сайта.

2. Просмотри нужные каталоги с размерами файлов:
  - Каталог проверяемого XML (`alta\result\<Кейс>\alta_import\` или `alta\result\<Кейс>\alta_export\`).
  - Каталог первички (`alta\source\<Кейс>\`).

3. Выйди в режим диалога, сформируй меню:
  - Проверяемый файл на выбор,
  - источник документов: `*.md` или первичка.

### 6.2 Исполнение (Проверка)
1. Прочитай целевой XML: `read_file "путь_к_файлу" "cp1251"`

2. Прочитай `master_data` и `operator_provided_data.md`.

3. Прочитай выбранные первичные документы (инвойс, упаковочный лист, транспортную накладную, тех. описание).
  - Если источник `*.md`, используй `read_file` для чтения из `alta\source\<Кейс>\<Поставка>\md\*.md`.
  - Если источник первичка: 
    - выполни шаги из раздела `7. Начало работы` файла `primary_tools.md` (Очистка мусора и Разведка),
    - загрузи первичные документы.

4. Проведи логический аудит строго по правилам Раздела 5.
    - Извлекай только meaningful-теги (начинаются на `G_`).
    - Сравнивай значения XML с данными из первички и `master_data`.
    - Фиксируй все расхождения, определяй статус (`Error` или `Warning`).

### 6.3 Формирование отчета
1. Подготовь содержимое отчета по формату из Раздела 3.
2. Запиши отчет в файл:
    - Для `pre_import`: `alta\result\<Кейс>\review\dt_check_review.md`
    - Для `post_export`: `alta\result\<Кейс>\review\GDT_check_review.md`
    - Используй команду `write_file`.

### 6.4 Завершение
1. Выйди в режим диалога.
2. Выведи на экран краткую сводку:
    - Количество найденных ошибок (`Error`).
    - Количество предупреждений (`Warning`).
    - Наличие критических блокеров.
3. Спроси оператора, нужны ли точечные правки в XML (если режим `pre_import` и найдены исправимые ошибки) или работа завершена.
