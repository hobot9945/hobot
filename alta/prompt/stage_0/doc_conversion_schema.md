# ИНСТРУКЦИЯ: Этап 0 — Конвертация первичных документов

## 0. Основные положения

### 0.1 Задача и поток данных
- **Вход:** `alta\source\<кейс>\...` (первичка: PDF, DOCX, XLSX, PNG, JPEG).
- **Выход:** `alta\source\<кейс>\md\` (файлы `.md`) + `alta\source\<кейс>\md\DOC_CONVERSION_REVIEW.md`.
- **Цель:** Перевести документы в машиночитаемый Markdown, сохранив все факты. Обработкой и верификацией займется Этап 1.0.
- **Режим:** Всегда выполняется при старте. Если `md\` уже содержит файлы — работай в режиме инкремента.

### 0.2 Главный приоритет
Главной задачей этапа является полное(дословное) распознавание текста и перенос его в раздел `Текст документа`. Остальные
части md-файлов желательны, но вторичны.

## 1. Правила извлечения данных и генерации

### 1.1. Разделы md-файла
1) META:
  - типовое имя (Контракт, Инвойс и т.д.)
  - полное путевое имя исходного файла
  - факт промежуточного преобразования PDF → JPEG с подробностями (число страниц, DPI), если было.

2) Текст документа.
   **АI ОБЯЗАН ОБЕСПЕЧИТЬ:**
  - **ПОЛНЫЙ (ДОСЛОВНЫЙ) ТЕКСТ ДОКУМЕНТА:** сохраняй текст в md-файле максимально точно, без урезаний сокращений, 
    выжимок, агрегации. Максимум допустимой трансформации - преобразование колонок таблиц в последовательные разделы 
    без потери содержания.
  - **БОЛЬШОЙ ОБЪЕМ ДАННЫХ НЕ СЛУЖИТ ПРИЧИНОЙ УРЕЗАНИЙ/СОКРАШЕНИЙ!!!**
  - Вставляй строку с оценкой уверенности распознавания **ПОСЛЕ КАЖДОЙ СТРАНИЦЫ** (`high|mid|low`).

3) Список смысловых блоков:
   Правила извлечения смысловых блоков текста и сопоставление с шаблонами раздела 6:

     - **Важно,** шаблоны используются для контроля состава документов, фиксируя обязательные смысловые блоки: 
       - поле `_audit`. Оно фиксирует число требуемых смысловых блоков документа. Массив, например `InvoiceGoods`,
         `TransportMeans` и др. считается одним смысловым блоком.
       - поле `_item_audit` - ожидаемое число смысловых блоков внутри элемента массива.

     - Для каждого поля из шаблона формируй ОТДЕЛЬНЫЙ смысловой блок. Блок обязан содержать:
        - заголовок с названием поля и его ID из схемы;
        - значение (как в первичке);
        - строку с оценкой уверенности (`high|mid|low`).

      Формат (пример для контракта):
      ```
      ### № контракта (01)
      - <значение как в документе>
      - <high|mid|low>
      ```

      Если поле отсутствует/не заполнено в документе:
      ```
      ### № контракта (01)
      - ПУСТО
      - high
      ```

      Если поле не распознано:
      ```
      ### № контракта (01)
      - НЕ РАСПОЗНАНО
      - low
      ```
    Для поля-массива (например, массивы товаров, транспортных средств, документов и т.д.), сначала сделай заголовок 
    массива, затем перечисли элементы массива. Ожидаемое число полей массива - `_item_audit`.

  **Полнота извлечения данных:**
  - **Все текстовые блоки, независимо от размера переносятся в md-файлы в полном объеме**.
  - **Данные, не требуемые шаблонами документов (раздел 6)** - если смысловые блоки документов не имеют соответствующих
    полей в шаблонах, они все равно должны извлекаться и помещаться в md-файл.
  - Полное покрытие полей **НЕ ПРИВОДИТ** к прекращению извлечения смысловых блоков.

4) Итог: В конец каждого `.md` добавь обязательный блок:
   ```
   ### Покрыто, полей:
   - X из Y (Y = `_audit` из схемы)

   ### Непокрытые поля: - (список полей)
   - <поле 1>
   - <поле 2>
      ...
   
   Если не покрыты поля массива:
   - <имя массива, номер элемента>
     - <поле массива 1>
     - <поле массива 2>
       ...
    
   ### Нижняя оценка уверенности:
   - <worst_confidence_in_file>

   ### Статус документа:
   - confirmed | pending

   ### Итог:
   - <краткий лог: использованные форматы, примененные конвертации, причина pending или "OK">
   ```
Термин "покрытие" означает сопоставление **непустых** принятых смысловых блоков полям шаблона.

**Шкала уверенности:**
  - `high`: текст чёткий, структура ясна, расхождений с образом нет.
  - `mid`: есть сомнения (размыто, сложный шрифт, склеенные ячейки), но данные читаемы.
  - `low`: критические сомнения (артефакты, пропуски, неоднозначность).

### 1.2 Общие правила

- **!!!ПОЛНОЕ И ТОЧНОЕ ИЗВЛЕЧЕНИЕ ДАННЫХ ИЗ ПЕРВИЧНЫХ ДОКУМЕНТОВ ИМЕЕТ АБСОЛЮТНУЮ ВАЖНОСТЬ ДЛЯ ВСЕЙ ПОСЛЕДУЮЩЕЙ ОБРАБОТКИ!!!**

- **Честное чтение:**
  - **СТРОГО ЗАПРЕШЕНЫ СОКРАЩЕНИЯ И ПЕРЕСКАЗЫ** - извлекай из первички только факты, максимально близко к тексту.
  - Извлекай данные как есть. Без интерпретации, агрегации или "улучшения". Опечатки оригинала сохраняй. 
    Недостающее не додумывай.

- **Классификация по содержанию:** Имя файла — не источник истины. Определяй тип документа по структуре и реквизитам. 
  Если тип не распознан — пометь как `[UNCLASSIFIED]` и добавь первые 10 строк в ревью.

- **Отбрасывай мусор** - не помещай в ревью файлы, которые явно не имеют отношения к ДТ.
 
- **Загрузка файлов:** 
  - TXT, MD - `read_file`;
  - XML - `read_file` в кодировке cp1251;
  - XLSX, DOCX, JPEG, PNG, TIFF, PDF - `drag_file_from_explorer_to_ai`

## 2. АЛГОРИТМ РАБОТЫ

### 2.0. Вспомни ограничения и правила записи на разных сайтах.

### 2.1. Сканирование: пройди рекурсивно `alta\source\<кейс>`. 
   - При наличии файлов с одинаковыми именами и разными расширениями бери приоритетный по удобству чтения: 
   `XLSX/DOCX` → готовые `PNG/JPEG` → `PDF` → динамическое конвертирование `PDF` в `JPEG` dpi=100 → 
   конвертирование `PDF` в `JPEG` dpi=150.
   - Если сайт замечен в некачественном OCR для `PDF` (описано в ограничения сайта, например arena, deepseek), то
     пропусти шаг обработки PDF и сразу переходи к динамическому конвертированию `PDF` в `JPEG`.

### 2.2. Выбор инкрементальное/полное обновление
    - Если каталог `md` не существует / пустой, нужна полная генерация,
    - иначе, сравни фактический состав md-файлов с их перечнем в `DOC_CONVERSION_REVIEW.md`, исправь его при необходимости.
    - Если правки затрагивают <50% строк файла → применяй патч.
    - Если >50% или структура кардинально изменилась → перегенерируй файл полностью.
    - **ВСЕГДА ПРОВЕРЯЙ И ОБНОВЛЯЙ ИТОГОВЫЙ БЛОК В КОНЦЕ ФАЙЛА**.
   
### 2.3. Порядок обработки и эффективность 
   - Обрабатывай документы по одному: 
      - загрузка, распознавание, генерация md-файла,
      - прочти начало и конец документа, убедись, что они правильно сформированы. Если обнаружишь несоответствия, выполни
        необходимы патчи или перегенерацию.
      - Переходи к следующему документу.
   - Многофайловые документы, например группу JPEG, как результат конвертации PDF, загружать одной директивой.

### 2.4. Качество извлечения данных

**Определения:**
- `problem_block` 
  - смысловой блок/страница, где `confidence != high` **по причине читаемости/распознавания** (размыто, артефакты, OCR-ошибки);
  - данные **не могут быть получены из-за проблемы сопоставления смыслового блока полю шаблона**.
  
  - **Не** считать `problem_block`, если поле:
    - отсутствует в документе (ПУСТО),
    - помечено как `НЕ ПРИМЕНИМО`,
    - требует нормализации (ISO-коды и т.п.), но текстовое значение читается (`high`).

**ИМПЕРАТИВ: ЗАПРЕШЕНО ФОРМИРОВАТЬ md-ФАЙЛ НА ОСНОВАНИИ ЧАСТИЧНО/ПЛОХО РАСПОЗНАННОГО ТЕКСТА:**
- после распознавания еще раз **проверь, что страница распознана ПОЛНОСТЬЮ**.
- Если полный текст документа считан с `confidence != high`, то есть, если хотя бы одна страница считана 
  с `confidence != high`, или
- если есть хотя бы один `problem_block`, то
**AI ОБЯЗАН** пройти попытки **строго по порядку 1→2→3→4**. Попытка считается “выполненной”, когда выполнено указанное 
действие и повторно извлечён `problem_block`.

**Запрещено** ставить `pending`, если:
- поле отсутствует в документе (ПУСТО),
- поле помечено как `НЕ ПРИМЕНИМО` (например, внутренний код Альты),
- текст читается (`high`), но поле требует только нормализации/приведения формата.

1) **Другие форматы (приоритеты):**  
   Если тот же документ доступен в альтернативных форматах — обработай **лучший доступный** по приоритету из раздела “Сканирование” и повторно извлеки `problem_block`.  
   Если платформа/ограничения сайта не позволяют использовать этот формат — зафиксируй в логе и переходи к шагу 2.

2) **PDF → JPEG @100:**  
   Если исходник PDF, то для страниц, содержащих `problem_block`, выполни преобразование PDF → JPEG **dpi=100** и повторно извлеки `problem_block`.  
   Если по ограничениям сайта PDF OCR считается некачественным — шаг 2 выполняется **всегда первым действием для PDF** (без попытки “обработать PDF напрямую”).

3) **PDF → JPEG @150 (только проблемные страницы):**  
   Если после шага 2 `problem_block` всё ещё `mid/low`, выполни **выборочное** преобразование **только нужных страниц** PDF → JPEG **dpi=150** и повторно извлеки `problem_block`.

4) **Фиксация и остановка по документу:**  
   Если после шагов 1–3 `problem_block` остаётся `mid/low`, пометь в итоговом блоке документа:
    - какие страницы/блоки,
    - какие попытки (1/2/3) выполнены,
    - что именно не удалось прочитать / что именно не удалось идентифицировать,
    - статус документа = `pending` (или `[OPERATOR_NEEDED]` при критичном поле).

   Если причина `pending` — **идентификация/сопоставление**, добавь в md-файл в раздел "### Итог:" отдельной строкой:
    - `Вопрос оператору: <один конкретный вопрос, привязанный к полю/ID>`

   Также добавь этот вопрос в `DOC_CONVERSION_REVIEW.md` в раздел "## 3. Незакрытые вопросы" (с указанием файла и блока/ID).

   После этого **разрешено переходить к следующему документу**.

### 2.5. **Генерация ревью:** 
После обработки всей пачки файлов создай/обнови `DOC_CONVERSION_REVIEW.md`.

**Внимание:** перед строкой шапки таблицы ВСЕГДА стоит пустая строка. Ее отсутствие - частая ошибка AI. 

### 2.6. **Блокеры:** Если есть документы со статусом `pending` (см. определение `pending` выше — только OCR/читаемость или идентификация/сопоставление):
- задай оператору вопрос(ы) (по одному);
- сохрани ответы оператора в `operator_provided_data.md` (append; обязательно укажи: файл, поле/ID, что подтверждено);
- обнови md-файлы и `DOC_CONVERSION_REVIEW.md` результатами диалога.

## 3. Очистка и правила именования
- Если в `alta\work\` накопились больше двадцати старых файлов, запроси у оператора удаление и удали их.
- Именование `.md` файлов строго соответствует имени исходника без расширения. Консистентность > семантика.

## 4. АДАПТАЦИЯ ПЛАТФОРМЫ (ai_url из сессии)
- **qwen.ai / chat.z.ai:** Нативное зрение сильное. PDF/PNG/JPEG загружай напрямую.
- **chat.deepseek.com:** Нативное зрение не используется. PDF, образы распознаются средствами сайта с низким качеством.
  Предупреди оператора, посоветуй исполнять этап 0 на других сайтах.
- **arena.ai:**
  - не обеспечивает перетаскивание XLSX, DOCX.  
  - Не обеспечивает качественное OCR для PDF-файлов. 
  - При обработке форматов **сразу переходи к конвертации PDF → JPEG**.

## 5. 🛠 Инструмент pdftojpeg.bat
Постраничное преобразование PDF-файла в JPEG формат.

**Путь:** `alta\service\script\pdftojpeg.bat`  
**Запускать из корня проекта:** `C:\...\hobot\`  
**Синтаксис:** `pdftojpeg.bat "полный_путь_к.pdf" <DPI> [номер_страницы]`

**Параметры:**
- `<DPI>`: обязательный. `100` → первая попытка, `150` → вторая попытка.
- `[номер_страницы]`: опциональный. Если указан, извлекается только эта страница. Если опущен - все страницы.

**Выход:** `alta\work\<имя_pdf>-<номер>.jpg` (нумерация с 1). Скрипт сам удаляет старые файлы с этим префиксом перед запуском.

**Правила применения:**
- Всегда указывай номер проблемной страницы (3-й параметр), чтобы не генерировать лишние файлы.
- После генерации сразу загружай полученные JPEG в чат через `drag_file_from_explorer_to_ai` и перечитывай блок.
- Если после 150 DPI уверенность всё ещё не `high` → ставь `[OPERATOR_NEEDED]` и переходи к следующему документу.

## 6. Шаблоны документов.
Шаблон описывает смысловые блоки документа, которые будут необходимы следующим этапам для формализации документов и
составления ДТ. Поля _audit, _item_audit служат цели определения покрытия документом полей шаблона, то есть позволяют
оценить полноту данных документа.

- _audit - число смысловых блоков в документе. Массив смысловых блоков, например массив товаров, считается одним блоком.
- _item_audit: 15 - число смысловых блоков внутри массива.
